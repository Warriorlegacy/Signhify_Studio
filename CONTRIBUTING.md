# Contributing to Signhify

This repo is connected to **Lovable** via two-way GitHub sync. Lovable is the primary editor and the deploy surface; Codex Cloud / local IDE / direct GitHub commits all work, but they have to play nicely with Lovable's automation.

Read this file before opening a PR or letting an agent (Codex, Claude, Cursor, etc.) commit to `main`.

---

## 1. Sync model

- Lovable ↔ GitHub is **bidirectional and automatic**.
- Every commit pushed to `main` is pulled into the Lovable preview within seconds and rebuilt.
- Every edit made in Lovable is pushed to `main` as a commit.
- Publishing to `signhify.lovable.app` (and the custom domain) happens **from Lovable**, not from GitHub Actions.

**Workflow for Codex / external agents:**

1. Work on `main` (or a feature branch + PR into `main`).
2. Push.
3. Wait for the Lovable preview to rebuild green.
4. Open Lovable → click **Publish** to ship.

---

## 2. Do not edit these files by hand

These are generated, managed by Lovable, or load-bearing for the sync. External agents must leave them alone:

- `src/routeTree.gen.ts` — auto-generated by the TanStack Router Vite plugin. Add/rename a file under `src/routes/`; the tree regenerates on the next dev/build.
- `src/integrations/supabase/types.ts` — regenerated from the live Supabase schema when migrations run. Don't hand-edit the type literals.
- `src/integrations/supabase/client.ts`, `client.server.ts`, `auth-middleware.ts`, `auth-attacher.ts` — Lovable Cloud wiring. Touch only if you know what changes.
- `bun.lockb` — let `bun add` / `bun remove` regenerate it. Don't hand-merge conflicts; re-run the install.
- `.lovable/` — Lovable project metadata.
- `supabase/config.toml` — managed by the Supabase integration.

If a generated file conflicts during a merge, **prefer the version on `main` and re-run the generator** (`bun install`, `bun run dev` once for routeTree, or a fresh migration for Supabase types) rather than resolving by hand.

---

## 3. Migrations

- New migrations go in `supabase/migrations/` with a **new timestamped filename** (`YYYYMMDDHHMMSS_description.sql`).
- **Never rewrite an existing migration.** It has already run against the live database; editing it in-place desyncs prod from the migration history.
- Every `CREATE TABLE public.<name>` must be followed in the same migration by explicit `GRANT`s and RLS policies (see the `<public-schema-grants>` rule the Lovable agent follows).
- Run/review migrations through the Supabase integration, not via raw `psql` against prod.

---

## 4. Server boundaries (TanStack Start)

- Client-imported server functions live in `src/lib/*.functions.ts` (or alongside the route).
- Server-only helpers live in `*.server.ts` and must **never** be imported from client code.
- Secrets (`LOVABLE_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, webhook secrets) are read inside `.handler()` via `process.env.*` — never at module scope, never via `import.meta.env`, never in client bundles.
- Protected server functions use `requireSupabaseAuth` and are called from components via `useServerFn`, **not** from public route loaders (SSR prerender has no session and will 401 the build).

---

## 5. Routes

- File-based routing under `src/routes/`. Create the route file **before** referencing it in `<Link to="...">`.
- Every page route needs a `head()` with a unique `title`, `description`, and Open Graph tags. No reusing the home page's meta.
- Root layout is `src/routes/__root.tsx`. Do not create `src/routes/_app/`, `app/layout.tsx`, or `src/pages/` — those belong to other frameworks and will create conflicting `/` routes.

---

## 6. Parallel editing

The #1 way to break the sync is to edit the same file in Lovable and Codex at the same time.

- If Codex is mid-task, **don't prompt Lovable** to touch the same area until Codex's PR is merged and pulled in.
- If Lovable is mid-task, wait for its commit to land on `main` before pulling in Codex.
- When in doubt, `git pull --rebase origin main` in Codex before pushing.

---

## 7. Roadmap

The execution plan lives at [`public/signhify-roadmap.md`](public/signhify-roadmap.md) and is also served at [`/roadmap`](https://signhify.online/roadmap). Codex tasks should reference the relevant week/section so progress stays legible.

---

## 8. Before you publish

- Preview rebuild is green in Lovable.
- No unresolved critical findings in the latest security scan.
- New public-facing routes have SEO metadata.
- Any new `public.*` table has `GRANT`s + RLS in the same migration.

Then: **Lovable → Publish**. Don't deploy from GitHub Actions.
